4. Rollout <details>

Use a fold when there's one main point and some supporting detail. The point stays visible, and the detail folds away.

Recommendation: ship behind a flag, then ramp to 100% over a week. If the hit rate falls, the flag turns the cache off without a deploy.

Why not a canary node?

Sessions are sticky to a node, so the canary would see a skewed set of tenants and give a misleading hit rate.

Benchmark setup

10M requests, Zipf α=1.1, 4 GB budget, single node.

How should it roll out? input type="radio"

5. Design at three depths data-tier="N"

Depth tiers add a switch for the whole page. Try the Overview / Shape / Detail bar in the bottom-right corner: it hides everything tagged deeper than the chosen level. Find-in-page still finds hidden text, and the page remembers the reader's level.

Overview: the cache sits between the API and Postgres.
Shape: the cache reads through on GET and invalidates on PUT/DELETE. Keys are tenant:session:id.
Detail: invalidations go out over Postgres LISTEN/NOTIFY, so every node drops stale keys within about 50 ms.

7. The change two columns

Two side-by-side columns show before and after, and they stack on narrow screens. This is a layout pattern, not a kit component: a few lines of grid CSS.

Before

(defn fetch [id]
  (metrics/timed :fetch
    (db/query id)))

Every request reaches Postgres.

After

(defn fetch [id]
  (metrics/timed :fetch
    (or (cache/get id)
        (cache/put! id (db/query id)))))

Only misses reach Postgres: about 85% fewer queries.

Keep the metrics hook? input type="checkbox"
