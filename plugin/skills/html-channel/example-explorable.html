How a hash table grows

A hash table finds a value by its key in about the same time whether it holds ten keys or ten million. That sounds impossible, since it has to look somewhere. We'll build one from a plain list, break it twice, and fix it twice, until the "about the same time" is earned.

Throughout, keys are blue, buckets are outlined boxes, collisions are red, and a resize is amber.

1. Looking through a list

Why we need anything better: the obvious way to find a key is to check every key until it turns up.

Here are 16 unsorted keys; drag the number to change how many. Press the button to look one up:

Notice that the work grows with the list: a key near the end costs as many checks as there are keys, and on average you check half of them.

Simplification: comparing two keys costs one unit here, whatever their length.

2. Turning a key into an address

Why: to skip the search, the key itself has to say where it lives. A hash function turns a key into a large number; the remainder after dividing by the number of buckets picks one:

i = h(k) \bmod m

Type any key, and change the number of buckets m = 8:

Notice that the same key always lands in the same bucket, and that changing m moves almost every key.

Simplification: h here is FNV-1a (32-bit), one real hash function chosen for being short; Python and Java use others.

3. One key per bucket

The naive model: give each bucket room for one key. A lookup is then a single step: hash, go there, done. Insert keys one at a time into 8 buckets:

Try the first three keys, then keep inserting until something goes wrong.

Notice that a collision arrives long before the buckets fill up: two keys hash to the same bucket, and this model has nowhere to put the second.

Simplification: the keys arrive in a fixed order, so the page behaves the same every time.

4. Collisions come early

Why the naive model fails: this is the birthday problem. With m equally likely buckets, the chance that n keys include at least one collision is

P(n) = 1 - \prod_{i=0}^{n-1} \left(1 - \frac{i}{m}\right)

Place 10 keys:

The classic case: 23 people, 365 birthdays already gives better than even odds.

Notice that the curve crosses one half near 1.18\sqrt{m} keys, so a thousand buckets are past even odds at about 38 keys.

Simplification: the formula assumes a perfect hash, where every bucket is equally likely and independent of the others.

5. Chaining: let buckets hold lists

The fix: since collisions can't be avoided, make them harmless. Each bucket holds a short list of keys, and a lookup walks only that list. Play the insertion of 24 keys into 8 buckets:

Notice that chains grow unevenly: some buckets stay empty while others hold four or five keys.

Simplification: new keys go to the end of a chain; some implementations put them first.

6. The load factor

Why: chaining works, but the chains get longer as keys pile in. The number that predicts how long is the load factor, keys per bucket:

\alpha = \frac{n}{m}

A successful lookup examines on average 1 + \alpha/2 - \alpha/2n keys. Insert 24 keys:

Notice that the measured average stays close to the formula: cost depends on \alpha, not on n alone. Keep \alpha bounded and lookups stay cheap however many keys there are.

Simplification: the formula is an average over random hash outcomes; one particular set of keys can do better or worse, as the bars show.

7. Growing: double and rehash

The second fix: to keep \alpha bounded, the table watches it. When an insert pushes it past a threshold of 0.75, the table doubles its buckets and moves every key to its new bucket.

Real tables pick different thresholds: Java's HashMap uses 0.75, and CPython's dict keeps its table at most two thirds full.

Notice that each resize moves every key, because h(k) \bmod m changes with m.

Simplification: CPython's dict uses open addressing, not chains; the two-thirds rule is what carries over.

8. Why moving everything is cheap on average

The payoff: a resize that moves every key sounds expensive, and it is, once. Count one unit per insert plus one per moved key, over 128 inserts:

Compare doubling over 512 inserts with adding 8 buckets each time.

Growing by a factor r moves at most

n\left(1 + \tfrac{1}{r} + \tfrac{1}{r^2} + \cdots\right) = \frac{n\,r}{r-1}

keys over n inserts: 2n for doubling, so each insert costs at most 3 units on average.

Notice that with doubling the spikes get rarer exactly as fast as they get taller, so the average saws up and down but never passes 3; adding a fixed 8 buckets makes the spikes come at a steady rate while they keep growing, and the average climbs without end.

Simplification: a resize is counted as one unit per moved key; allocating the new table costs extra in practice.

Limits of this model

  • Every curve assumes a good hash. A poor one, or keys chosen by an attacker, puts many keys in one bucket; Java's HashMap turns a chain of 8 or more into a balanced tree to bound the damage.
  • Counting key comparisons ignores memory. On real hardware, following chain pointers misses the cache, which is why many tables (CPython's among them) use open addressing instead of chains.
  • One resize still stalls the insert that triggers it. Systems that can't afford the pause, such as Redis, move keys a few at a time over many operations.
  • Tables here never shrink after deletions; real ones may.
